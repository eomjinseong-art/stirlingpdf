1. 먼저, Stirling PDF가 무엇인지부터

Stirling PDF는 PDF 합치기, 나누기, 페이지 회전, 압축, 이미지 변환, OCR 같은 여러 문서 작업을 브라우저 화면에서 수행할 수 있게 만든 오픈소스 PDF 처리 애플리케이션입니다[cite: 1]. 중요한 점은 단순한 정적 HTML 소스가 아니라 화면 뒤에서 Java 애플리케이션과 LibreOffice, Tesseract 같은 도구가 실제 파일을 처리한다는 사실입니다[cite: 1].

따라서 일반적인 HTML 사이트처럼 GitHub에 올리고 Vercel에 연결하는 것만으로는 전체 기능이 실행되지 않습니다[cite: 1]. Vercel은 소개 페이지와 광고를 보여주는 프론트엔드 역할에 적합하고, Stirling PDF는 Docker 컨테이너를 실행할 수 있는 별도 서버가 담당해야 합니다[cite: 1].

한 문장으로 정리하면

Vercel은 사용자가 보는 “가게”, Stirling PDF 서버는 문서를 실제로 처리하는 “작업장”입니다[cite: 1].

2. 제가 선택한 구조: 화면과 처리 서버 분리

처음에는 파일 하나로 끝날 것이라 생각하기 쉽지만, 실제로는 두 개의 배포물이 서로 역할을 나눕니다[cite: 1]. 사용자는 내 도메인으로 접속하고, 페이지 안의 iframe이 처리 서버 화면을 불러옵니다[cite: 1].

구성담당 역할적합한 서비스
프론트엔드브랜드, 설명 글, 광고, 이용 안내, iframeVercel + GitHub[cite: 1]
처리 서버PDF 업로드, 변환, OCR, 결과 다운로드Docker가 계속 실행되는 VPS[cite: 1]
도메인·HTTPS안전한 접속, 혼합 콘텐츠 방지DNS + 리버스 프록시[cite: 1]

왜 iframe을 골랐나

REST API로 직접 UI를 만들 수도 있지만 파일 업로드·진행 상태·오류 처리를 모두 구현하려면 손이 많이 갑니다. iframe은 Stirling PDF가 제공하는 완성된 화면을 그대로 활용하므로 검증 속도가 빠릅니다[cite: 1]. 대신 프레임 보안 헤더나 쿠키 정책 때문에 막힐 수 있다는 점을 주의해야 합니다[cite: 1].

3. 실제 구축 과정: 처음부터 차근차근

운영용 권장 사양은 기능과 동시 사용자에 따라 다릅니다[cite: 1]. 공식 가이드는 기본 배포에 최소 2GB RAM을 안내하며, OCR과 Office 변환은 특히 메모리와 CPU를 많이 소모합니다[cite: 1].

1단계: 로컬에서 먼저 성공시키기

먼저 내 PC에서 공식 이미지를 실행해 정상 화면이 뜨는지 확인합니다[cite: 1].

docker run -d \
  --name stirling-pdf \
  -p 8080:8080 \
  -v ./stirling-data:/configs \
  docker.stirlingpdf.com/stirlingtools/stirling-pdf:latest

2단계: Docker Compose로 운영 설정 만들기

운영 환경에서는 설정을 기록하고 관리하기 편한 Compose를 활용합니다[cite: 1].

services:
  stirling-pdf:
    image: docker.stirlingpdf.com/stirlingtools/stirling-pdf:latest
    container_name: stirling-pdf
    ports:
      - "8080:8080"
    volumes:
      - ./stirling-data/configs:/configs
      - ./stirling-data/logs:/logs
    environment:
      SECURITY_ENABLELOGIN: "true"
      SYSTEM_DEFAULTLOCALE: "ko-KR"
    restart: unless-stopped

4. 제가 막혔던 지점과 해결 방법 (트러블슈팅)

문제 1. Vercel 배포는 성공했는데 PDF 기능이 없다

원인: 정적 HTML만 배포했고 실제 처리 서버가 없기 때문입니다[cite: 1].
해결: Docker 서버를 별도로 실행하고 그 HTTPS 주소를 연결합니다[cite: 1].

문제 2. iframe 영역이 하얗거나 "refused to connect"가 뜬다

원인: 프레임 보안 헤더, 잘못된 주소, 서버 중단이 대표적입니다[cite: 1].
해결: 새 탭에서 주소를 먼저 열어 서버 생존 여부를 확인하고 개발자 도구에서 X-Frame-Options 오류를 확인합니다[cite: 1].

문제 3. HTTPS 페이지에서 HTTP 도구가 안 뜬다

원인: 브라우저의 Mixed Content 차단 때문입니다[cite: 1].
해결: 처리 서버에도 유효한 HTTPS 인증서를 적용해야 합니다[cite: 1].

문제 4. 업로드하다 413 오류가 난다

원인: 프록시나 애플리케이션의 업로드 제한 용량을 초과했기 때문입니다[cite: 1].
해결: 리버스 프록시와 Stirling PDF 설정의 최대 파일 크기 제한을 함께 조정합니다[cite: 1].

운영 시 주의사항

공개 웹서비스는 파일이 처리 서버로 전송되므로 전송 암호화, 임시 파일 삭제 주기, 로그 정책을 반드시 점검해야 합니다[cite: 1].
